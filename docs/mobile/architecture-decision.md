# Mobile architecture decision

Decision date: 18 October 2026.

This repository already contains a React Native application. The decision is to keep that application and connect it to the current PHP house. A second mobile codebase is not being started.

## Decision

| Choice | What it is |
| --- | --- |
| Client | React Native with TypeScript |
| Navigation | Expo Router, file routes under `src/app` |
| Tooling | Expo SDK 58, with EAS for store binaries |
| Credentials on device | `expo-secure-store` (Keychain on iOS, Keystore on Android). Web preview uses session storage and drops it when the tab closes. |
| Images | `expo-image-picker`, only when a member chooses a picture |
| Links | `expo-linking`, scheme `gosolo` |
| Server | The existing PHP application, reached at `/api/v1` |
| Database | The existing SQL database, reached only by that PHP application |

Expo stays because this SDK already provides the store build path, secure storage, image selection, and native linking that the companion needs. The app is not a WebView and not a packaged copy of the website.

## What was rejected

- A WebView, or the website shipped as the app.
- A progressive web app described as a native build.
- Node.js as a product backend.
- Supabase authentication, tables, or storage.
- A second member database or a second account system.
- Two unrelated mobile implementations. Platform files are added only when a store binary needs them, and `ios/` and `android/` are generated by EAS rather than committed.
- Phone push in this release. The production house has `notices` and PHP `mail()`. It has no device-token table and no push provider. Registering a phone token would invent a backend. In-app notices are the notification channel until that exists.

## How the phone reaches the house

```
iOS app
        \
         HTTPS JSON  /api/v1
        /
Android app
        |
Existing PHP application
        |
Existing SQL database
```

The app never receives a database host, name, user, password, or connection string.

Sign-in checks the existing `password_hash`. The reply is a short-lived access token and a rotating refresh token. Only SHA-256 hashes are stored, in the proposed `api_tokens` table. The website's `gosolo` cookie is not the mobile credential.

Authorization, ownership, visibility, blocks, and conversation eligibility stay in the PHP functions the website already uses. The screen is not a security boundary.

Until `host/app/api.php`, `host/app/bootstrap.php`, and `host/sql/update-api.sql` are uploaded, `EXPO_PUBLIC_API_URL` stays blank. The app then runs a labeled on-device preview. That preview is not the community. `https://gosolo.co.network/api/v1` currently returns the website's HTML 404.

## Relationship to the audit

Table names, lifecycle values, and permission rules come from `docs/mobile/current-architecture-audit.md`. Where this app previously assumed a display-name confirmation for deletion, it now uses the website rule: the word `DELETE`, then `DELETE FROM users`.

Columns added only in `host/sql/update-api.sql` are proposed. They are not described as already present on the live server.
